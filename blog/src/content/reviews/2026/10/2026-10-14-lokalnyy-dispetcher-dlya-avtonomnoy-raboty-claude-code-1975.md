## Коротко
Разработчик создал AIWorks — локальную систему, которая ведёт многошаговые задачи Claude Code, отдельно проверяет изменения и передаёт человеку только решения, требующие его участия. За сутки на собственном репозитории система провела 63 изменения через проверку, но опыт также выявил ограничения платформы, квот и достоверности агентских отчётов.

## Контекст
Автор — разработчик корпоративных систем, который по вечерам использует Claude Code для личных проектов. Устав от постоянных подсказок агенту, ручной проверки результата, остановок из-за лимитов и потери контроля над несколькими проектами, он создал AIWorks — локальный диспетчер с запретом на автоматическое слияние и деплой. Проект опубликован под лицензией MIT на github.com/netbka/aiworks.

## Главное
- AIWorks — локальный диспетчер на Node.js с состоянием в SQLite и публикацией результатов в GitHub; при отсутствии задач он не вызывает модели.
- Автор заранее зафиксировал ограничения: план утверждается один раз, сборщик и проверяющий — разные сессии, слияние и деплой запрещены, человека беспокоят только по решениям, которые не может принять система.
- Каждый шаг получает отдельный git worktree и пакет задачи: цель, критерии приёмки, разрешённые к изменению файлы и правила проекта. Запуск записывается в базу до старта.
- Сборщик — Claude Code в безынтерфейсном режиме без пользовательских настроек, хуков, MCP-серверов и памяти; он работает внутри Windows Job Object с таймаутом и сердцебиением.
- Проверяющий — новая read-only-сессия на том же коммите. Она должна подтвердить хэш коммита и отпечаток отчёта сборщика, а также повторить тесты.
- План может задавать цепочку провайдеров claude-cli с моделью opus, codex-cli и cursor-cli; резервный исполнитель включается из-за проблем провайдера, но не для обхода отказа проверки.
- Для восстановления после сбоев предусмотрены сердцебиение, подхват уже работающего воркера и задачи планировщика Windows, запускающие диспетчер и дашборд при входе и затем каждые пять минут.
- GitHub GraphQL-квота закончилась при публикации пул-реквестов; автор перевёл вызовы на REST через gh api и усилил проверку того, что именно считается подтверждённым слиянием.
- Windows-тест коллизии имён Readme.md и README.md прошёл локально, но упал на Linux из-за различий файловых систем и реалистичности поддельного листинга каталога.
- Чтобы отчёты не выдумывали статистику, сборщик должен дословно копировать строки итогов тестов, а проверяющий сверяет числа с собственным повторным запуском; неверный подсчёт считается блокирующей проблемой.
- За 24,5 часа было обработано 63 пул-реквеста, 18 из них слиты ночью; максимум — четыре параллельные линии, около 45 минут на типичный шаг и рост набора тестов с 385 до 760.
- Человек сохраняет право слияния и деплоя; дашборд показывает только действия, требующие его внимания, а ожидание лимитов и автоматические повторы не считаются поводом для уведомления.

## Как сделано
AIWorks работает как постоянно запущенный процесс Node.js на домашнем компьютере с Windows. Состояние хранится в локальной SQLite, а результаты публикуются в GitHub. Когда задач нет, к модели не обращается. Задачи задаются JSON-планом с версией разрешения, целью, критериями приёмки, зависимостями и допустимыми исполнителями.

Для каждого шага система создаёт отдельный git worktree и запускает Claude Code без интерфейса, личных настроек, хуков, MCP-серверов и памяти пользователя. Воркер работает в Windows Job Object с таймаутом и контролем сердцебиения. Результат должен включать валидный JSON и хэш чистого коммита: словесного заявления о завершении недостаточно.

Затем свежая сессия проверяющего открывает тот же коммит в отдельной копии, доступной только для чтения, повторяет тесты и сверяет хэш и отпечаток отчёта сборщика. При замечаниях запускается новый раунд. После успешной проверки AIWorks отправляет именно проверенный коммит и открывает один пул-реквест, предварительно проверяя, не создан ли он уже. Слияние и деплой система не выполняет. Claude — основной исполнитель; Codex и Cursor предусмотрены как запасные варианты, но переключение происходит только при проблеме самого провайдера, а не ради обхода проваленной проверки.

## Результаты
В эксперименте 12–13 октября AIWorks работал над собственным репозиторием 24,5 часа. Через независимую проверку прошли 63 завершённых изменения в виде пул-реквестов; 18 из них были слиты между полуночью и 7 утра, а на пике одновременно работали четыре независимые линии. Типичный шаг сборки и проверки занимал около 45 минут. Число тестов выросло с 385 до 760; около 25 тысяч строк — примерно 53% кода AIWorks — автор связывает с работой через диспетчер. Сборка обычно обходилась примерно в $5, проверка — в $2–3; более ранняя оценка с учётом повторов составляла около $10 за доставленный шаг. Автор оценивает сэкономленное время координации примерно в 16 часов, исходя из 15 минут ручной работы на каждое из 63 изменений.

## Ограничения
Система рассчитана только на Windows: воркеры используют Windows Job Object и на других ОС не запускаются. Основной провайдер — Claude Code; Codex и Cursor служат лишь частичными резервами, причём Codex на Windows не подходит для проверки кода в read-only-песочнице, где нельзя устанавливать зависимости и создавать временные файлы. Независимая проверка снижает риск, но не устраняет его, поэтому решение о слиянии остаётся за человеком. Автор описывает один интенсивный прогон на собственном проекте, а не независимое сравнение или длительную эксплуатацию на разных репозиториях. Среди обнаруженных проблем — исчерпание GitHub GraphQL-квоты, платформозависимый тест, неверные числа в отчётах агента и противоречивые вердикты проверяющего. Некоторые исправления и правила на момент публикации ещё находились в работе; дашборд оставался новым и местами шероховатым. Оценка экономии времени приблизительная, а стоимость зависит от повторных запусков и расхода лимита подписки.

## Что взять себе
- Чтобы автономная работа была управляемой, заранее задайте неизменяемые границы разрешения и оставьте слияние и деплой человеку.
- Не полагайтесь на самоотчёт модели: требуйте проверяемый артефакт вроде хэша коммита, запускайте независимую read-only-проверку и сверяйте отчёт с реальным выводом инструментов.
- Проектируйте повторы и восстановление с учётом квот и сбоев: общая пауза на аккаунт и идемпотентное создание пул-реквестов предотвращают лишние запросы и дубли.
- Проверяйте тесты на целевых платформах: успешный локальный прогон не гарантирует корректность в Linux CI или при других особенностях файловой системы.
- Автоматизация может сэкономить время на координации, но результат одного проекта и грубая оценка экономии не доказывают, что система безопасна для произвольного кода.
