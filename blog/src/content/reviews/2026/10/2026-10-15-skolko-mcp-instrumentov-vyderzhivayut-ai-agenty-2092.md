## Коротко
Автор проверила распространённое правило «меньше MCP-инструментов — выше точность» на трёх агентских клиентах. В протестированном диапазоне до 100 инструментов топовые модели почти не теряли точность, но способ загрузки схем, качество названий и выбор модели влияли на расход токенов и отдельные ошибки.

## Контекст
Автор проанализировала 91 публичный материал о проектировании MCP-серверов и обнаружила, что рекомендации ограничивать набор инструментов часто приводятся без измерений. Затем она провела собственные тесты в Claude Code, Codex CLI и Antigravity, чтобы выяснить влияние количества и группировки инструментов, а также их названий.

## Главное
- Из 91 рассмотренного источника 38 советовали уменьшать число инструментов, но лишь 10 измеряли связь количества инструментов с точностью; конкретную числовую границу называли 20 источников.
- Тест охватывал 5–100 инструментов, включая похожие названия вроде pdf_compress, pdf_optimize и image_compress; было 18 задач, десять из них неоднозначные.
- В Claude Code с Opus 5.5 режим ToolSearch по умолчанию сначала показывает названия и подгружает схемы по запросу; без поиска схемы сразу включаются в промпт.
- Codex CLI с GPT-6.1-sol использует code mode: модель ищет определения инструментов кодом, а Antigravity с Gemini 3.1 Pro показывает названия и открывает файл схемы по запросу.
- При отдельных инструментах топовые модели дали правильный результат во всех проверенных условиях до 100 инструментов; правило «меньше инструментов — выше точность» в этом эксперименте не подтвердилось.
- Сгруппированные инструменты дали разные эффекты: в Claude Code без поиска семь инструментов стоили по токенам примерно как 14 отдельных; с ToolSearch группировка почти не меняла расход, а Antigravity с Gemini 3.1 Pro достиг 89% точности.
- При расплывчатых именах Gemini в 34 из 72 прогонов сначала открыл схему не того инструмента, а в десяти пробовал неверный вызов с пустыми аргументами; тестовый сервер такие вызовы отклонял.
- В дешёвых моделях GPT-Reserve четырежды вызвал не тот инструмент; у Gemini 3.8 Flash три ошибки из четырёх были связаны с API и числовым enum, который API Gemini не принимал.
- В API Claude названия инструментов ограничены 64 символами, точки не допускаются; префикс mcp_&lt;server>__&lt;tool> расходует тот же бюджет имени. API Gemini принимает в enum только строки, что вызвало сбои со схемами поворота.

## Как сделано
Создан тестовый MCP-сервер с реалистичными файловыми и документными инструментами: до 100 отдельных инструментов, семь сгруппированных инструментов на 50 операций и вариант с расплывчатыми названиями. Инструменты не выполняли реальные операции; корректность оценивалась по журналу вызовов. Агентам давали 18 задач, включая неоднозначные, при размерах набора от 5 до 100 и по два прогона на условие.

Проверялись Claude Code с Opus 5.5, Codex CLI с GPT-6.1-sol и Antigravity с Gemini 3.1 Pro. В Claude Code сравнили режим ToolSearch, где сначала видны названия, и загрузку всех схем в промпт. Дополнительные 1404 прогона провели на Haiku 5.5, GPT-Reserve и Gemini 3.8 Flash (low). Автор также сравнивала токены и стоимость, а результаты и сырые логи выложила на GitHub.

## Результаты
В отдельных инструментах топовые модели прошли все проверенные задачи правильно при наборах до 100. При расплывчатых названиях все 276 прогонов с топовыми моделями также завершились правильными вызовами, но модели чаще искали схемы: Claude Code с ToolSearch загружал в среднем 7,6 схемы вместо 1,6 на прогон при 100 инструментах; расход входных токенов вырос на 21%, а у Gemini — на 38%.

Среди дешёвых моделей 1288 из 1296 прогонов с отдельными инструментами были правильными; появились четыре вызова неверного инструмента GPT-Reserve, а у Gemini Flash три сбоя были связаны с отклонением API схемы enum. Для Claude Code с 100 инструментами ToolSearch снизил входные токены за прогон на 59% относительно загрузки всех схем, но это не означало меньшую цену: указанные стоимости составили $0,047 с поиском и $0,038 без него. Haiku обходился примерно в $0,0012 за прогон.

## Ограничения
Это тест фейковых инструментов только для файлов и документов, с ограниченным набором задач и моделей; реальные побочные эффекты серверов не проверялись. Старые и небольшие открытые модели не тестировались, а длинные рассуждения и вытеснение контекста не измерялись. Расплывчатые имена проверялись при хороших описаниях, а не при плохих названиях и описаниях одновременно. Наборы и условия тестировались не во всех клиентах полностью; в частности, часть прогонов Codex с расплывчатыми именами отсутствует из-за лимита подписки. Результаты отражают состояние на октябрь 2026 года и не доказывают, что выводы сохранятся для других серверов, моделей или задач.

## Что взять себе
- Не ограничивайте набор инструментов ради точности только на основании общих советов: проверьте конкретные модели и задачи своего агента.
- Учитывайте реализацию клиента: отложенная загрузка схем может экономить контекст, но добавлять вызовы и не обязательно снижать цену.
- Используйте конкретные названия по схеме «действие + объект» и различимые описания, особенно если клиент сначала показывает модели только имена.
- Не объединяйте операции в крупные инструменты без тестирования на целевых клиентах и моделях; группировка может по-разному влиять на точность и стоимость.
- Проверяйте совместимость схем с API и обязательность аргументов: некорректный enum или пустой вызов на реальном сервере способен привести к отказу или побочному действию.
