## Коротко
Автор разбирает три сбоя рабочего агента в n8n: клиенту отправлялась пустота при успешном статусе, длинное сообщение получило Bad request, а каталог выдавал все товары. Главный вывод — проверять фактический текст после очистки и отправлять, сохранять успешные executions и повторно тестировать защиту при смене версии нод.

## Контекст
Автор разрабатывает self-hosted ИИ-агентов на n8n для заказчиков. В кейсе агент ателье украшений обрабатывает сообщения в Instagram Direct, собирает анкету и создаёт сделки в amoCRM; в стеке также Redis с TTL памяти 30 дней и LangChain. Рабочий процесс вырос с 64 до 88 нод; вместо DeepSeek V4 Pro используется z-ai/glm-5.3-flash через OpenRouter, резервная модель — qwen/qwen3.8-flash.

## Главное
- Агент работает в self-hosted n8n; память диалога хранится в Redis 30 дней, сделки создаются в amoCRM.
- Модель изменилась на z-ai/glm-5.3-flash через OpenRouter; резервная — qwen/qwen3.8-flash. В примере карточки генерации указаны 766 reasoning-токенов и 105 видимых токенов.
- Форматтер удалял протокольные теги вроде [VERDICT:…] и [TASK:NONE], но оставлял переносы и пробелы. Проверки непустой строки хватало, чтобы отправить запрос, хотя клиент видел пустоту.
- Успешные executions не сохранялись из-за saveDataSuccessExecution: none, поэтому расследование было затруднено. Автор включил Save successful production executions.
- В документации Meta автор нашёл лимит текста сообщения 1000 UTF-8 байт. Русская строка из 570 символов заняла 1030 байт; превышение лимита в конкретном Bad request пока не доказано.
- В ноде get_product_catalog1 была включена генерация схемы из JSON-примера, хотя в jsonSchemaExample лежала сама JSON Schema. Следствие — category отсутствовала на верхнем уровне, и код инструмента выбирал весь каталог по умолчанию.
- Исправление каталога: выбрать Schema Type — Define using JSON Schema и перенести схему в Input Schema.

## Как сделано
После жалобы автор включил сохранение успешных production executions: ранее настройка saveDataSuccessExecution: none скрывала успешные прогоны. Проследив выполнение до отправки, он обнаружил, что модель могла вернуть только служебные теги, которые очищались форматтером до пробелов и переносов. Проверка непустой строки пропускала такой результат, поэтому отправлялся запрос с пустым для человека содержимым.

## Результаты
Выявлена причина тихой отправки пустого сообщения: служебный вывод модели проходил проверку непустого ответа, а после удаления тегов оставался непустой пробельный шлейф. Автор предложил выражение для выбора очищенного ответа или заглушки и сохранения визуальных абзацев через NBSP. Также найдено неверно настроенное JSON Schema поле, из-за которого инструмент каталога получал не category и возвращал весь каталог. Ошибка Bad request пока не подтверждена: автор предполагает превышение лимита 1000 UTF-8 байт, но реальный текст упавшего запроса ещё не проверил.

## Ограничения
Статья описывает один рабочий проект; значения ключей и названия в примерах изменены. Для Bad request нет сырого HTTP-лога и кода ответа, поэтому лимит в 1000 байт — гипотеза, требующая проверки messageText из упавшего execution. Предложенная обрезка до 950 байт проверена только в обычном Node, не в n8n и не на проде; она может удалить важный хвост анкеты, например телефон. Устаревание Reasoning_Validator выведено из кода, но автор не воспроизвёл его на живом workflow. Поведение .item проверялось лишь на тестовой топологии; песочница была n8n-workflow 2.25.7, прод — v2.41.4.

## Что взять себе
- Проверяйте не только непустоту ответа модели, а наличие полезного человеческого текста после форматирования — непосредственно перед отправкой.
- Сохраняйте успешные executions в проде, если они нужны для диагностики тихих сбоев.
- При интеграции с API проверяйте лимиты в байтах UTF-8, особенно для кириллицы и эмодзи; гипотезу о причине ошибки подтверждайте по реальному запросу.
- После обновления n8n или LangChain проверяйте, что валидаторы всё ещё видят ожидаемые поля и действительно срабатывают.
- В режиме Generate From JSON Example передавайте пример данных, а не JSON Schema.
