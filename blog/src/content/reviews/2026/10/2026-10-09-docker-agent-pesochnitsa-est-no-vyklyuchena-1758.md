## Коротко
В Docker Desktop 4.63+ уже предустановлен `docker agent` — среда для создания ИИ-агентов через YAML и подключения MCP-инструментов. Автор считает её VM-песочницу с запретом исходящего трафика хорошо спроектированной, но подчеркивает: по умолчанию она отключена, поэтому запуск без флага может дать агенту доступ к хосту от имени пользователя.

## Контекст
Автор изучил репозиторий и документацию Docker Agent, не запуская инструмент. Он сопоставляет его с ранее созданным им защитным механизмом для собственного кодового агента и рассматривает главный вопрос безопасности: как ограничить действия агента, а не только его доступ к контексту.

## Главное
- `docker agent` предустановлен в Docker Desktop 4.63 и новее.
- Агенты задаются декларативно через YAML; доступны провайдеры OpenAI, Anthropic, Gemini, Bedrock, Mistral, xAI и Docker Model Runner.
- В `toolsets` можно объявить инструменты типов `filesystem`, `shell` и `mcp`; MCP-серверы бывают локальными, удаленными и Docker-based.
- Песочница использует VM Docker Sandboxes: рабочая папка монтируется для чтения и записи, каталоги конфигурации и kits — только для чтения, остальные файлы хоста скрыты.
- Сетевой доступ песочницы работает по принципу default-deny; разрешенные адреса можно задавать через `runtime.network_allowlist` или `docker agent sandbox allow`.
- Песочница отключена по умолчанию: запуск `docker agent run agent.yaml` выполняется на хосте; для явного включения есть `docker agent run --sandbox agent.yaml`.
- Автор рекомендует закреплять удаленные kits и образы по digest, поскольку изменяемые теги мешают воспроизводимости.
- Остановленные песочницы автоматически не удаляются; для принудительного удаления состояния указана команда `sbx rm --force <name>`.
- Документация называет автоматическое редактирование секретов best-effort; облачный режим, по статье, не загружает ключи API с хоста.
- Инструмент поддерживает OpenTelemetry-трейсинг, но автор считает его недостаточным для неизменяемого аудита действий агента.

## Как сделано
Агенты описываются декларативной YAML-конфигурацией. В блоке `toolsets` задаются доступные средства, например `filesystem`, `shell` и `mcp`; система поддерживает модели нескольких поставщиков, а также локальные, удаленные и контейнерные MCP-серверы.

При включенной песочнице агент запускается в VM Docker Sandboxes. Рабочая папка доступна для чтения и записи, конфигурация агента и kit-каталоги — только для чтения, прочие файлы хоста не видны. Исходящие сетевые соединения блокируются по умолчанию, кроме разрешенных для запуска адресов; список можно расширить через `runtime.network_allowlist` или `docker agent sandbox allow`.

Песочницу включают командой `docker agent run --sandbox agent.yaml`, параметром `runtime: sandbox: true` в YAML или при создании alias, например `docker agent alias add safe-coder myorg/coder --sandbox`. Автор также советует закреплять удаленные kits и образы по digest и удалять оставшееся состояние командой `sbx rm --force <name>`.

## Результаты
Автор пришел к выводу, что архитектура песочницы — изоляция в VM, ограниченные монтирования и default-deny для исходящего трафика — выглядит сильнее обычных hook-ограничений и может сдерживать эксфильтрацию даже при prompt injection. Однако без явного включения `--sandbox` агент работает на хосте, и сочетание `shell` с `filesystem` может подвергнуть риску данные и ресурсы, доступные учетной записи пользователя. В статье нет собственных измерений или тестов поведения инструмента.

## Ограничения
Это разбор исходников и документации, а не практическое тестирование: автор не запускал Docker Agent и принимает точность описания песочницы на веру. Изоляция не устраняет вредоносные инструкции в описаниях MCP-инструментов; редактирование секретов обозначено как best-effort, остановленные песочницы не удаляются автоматически и могут занимать платное хранилище. Изменяемые теги ухудшают воспроизводимость, а OpenTelemetry-трейсы не являются криптографически защищенным аудиторским журналом. Автор также отмечает, что Docker может изменить значение по умолчанию в будущей версии.

## Что взять себе
- Проверяйте, включена ли песочница: наличие защиты в продукте не означает, что она действует при обычном запуске.
- Перед использованием изучайте состав `toolsets`; особенно осторожно относитесь к совместному предоставлению `shell` и `filesystem`.
- Рассматривайте определения MCP-инструментов как исполняемую часть цепочки доверия: изоляция VM не фильтрует инструкции, которые модель читает в описаниях инструментов.
- Закрепляйте версии образов и kits по digest и удаляйте ненужные песочницы, чтобы ограничить риски невоспроизводимости и хранения секретов.
