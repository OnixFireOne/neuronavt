## Коротко
В тесте на двух узлах с NVIDIA B200 сравнили перенос KV-кэша через InfiniBand с GPUDirect и TCP/Ethernet при раздельном выполнении prefill и decode. RDMA заметно сократил время до первого токена и оказался надёжнее на тяжёлых профилях; результаты указывают на узкое место в программном пути TCP, а не в пропускной способности сети.

## Контекст
Автор статьи — инженер или исследователь, проводивший испытания на рабочих стендах; имя, должность и организация не указаны. Работа исследует, как транспорт KV-кэша влияет на производительность и отказоустойчивость disaggregated inference, где prefill и decode работают на разных узлах. Использовались MiniMax-M3 MXFP8, sglang и кластер из двух узлов по восемь NVIDIA B200.

## Главное
- Стенд состоял из двух узлов по 8 NVIDIA B200: node-a обслуживал prefill и router, node-b — decode; обе роли работали с TP=8.
- Модель — MiniMax-M3 MXFP8, 31 shard, размер артефакта 443 771 536 556 байт; движок — sglang 0.0.0.dev1+g56e290315.
- M1 включала пять профилей ISL/OSL: 128/128, 2048/256, 8192/256, 32768/256 и 2048/2048; проверялись конкурентности 1, 8 и 32, по пять повторов на транспорт.
- При concurrency=8 на валидных прогонах IB снизил TTFT в 5,4 раза для 128/128, в 11,5 раза для 2048/256 и в 5,8 раза для 8192/256; throughput вырос соответственно в 3,2, 2,8 и 3,8 раза.
- Все 75 прогонов RDMA/InfiniBand прошли; у TCP успешны 44 из 75. Для 2048/2048 и 32768/256 TCP отказал во всех пяти повторах при каждом из уровней конкурентности.
- Цепочка TCP-отказа: CUDA memory copy out of memory → KVTransferError timeout after 300 s → завершение prefill → HTTP 503 от router. Microbenchmark воспроизвёл этот класс отказа.
- По счётчикам портов KV действительно шёл по выбранной фабрике. TCP достигал максимум 8,7 Гбит/с из 200 Гбит/с; IB — максимум 61,7 Гбит/с при измеренном суммарном потолке NDR около 2933 Гбит/с.
- Изолированный transfer_engine_bench показал преимущество GDR над host staging на 6,29% для записи и 6,50% для чтения; TCP write из VRAM завершился ошибкой.
- В M2 nixl работал через InfiniBand и передавал сопоставимый объём данных с mooncake — различие ib_tx было около 1% или меньше; абсолютные TTFT M2 авторы считают несопоставимыми с прогретой M1.
- В отдельной проверке triton снизил TTFT относительно fa4 на 33,5–44,4%, но у backend'ов различались KV-layout: page_size=None у triton и page_size=128 у fa4.

## Как сделано
На node-a выполнялись prefill и router, на node-b — decode; обе роли использовали TP=8. Сравнивались RDMA/InfiniBand через восемь NDR-портов 400G с GPUDirect и TCP/Ethernet через bond0, LACP 2×100G, MTU 9000. Основная конфигурация: sglang 0.0.0.dev1+g56e290315, mooncake, deep_gemm, attention backend fa4 с page size 128, CUDA 13.0.1 и MLNX-OFED 24.10; mem-fraction-static=0.85, chunked prefill 8192, max running requests 20.

В матрице M1 проверили профили входа/выхода 128/128, 2048/256, 8192/256, 32768/256 и 2048/2048, три значения конкурентности и пять повторов для каждого транспорта: всего 150 прогонов. Авторы собрали 268 записей с учётом дополнительных испытаний. Измерения охватывали потолок сети (L0), изолированный transfer_engine_bench (L0b), реальные маршруты по счётчикам портов (L1), метрики sglang (L2) и пользовательские метрики bench_serving (L3). Стек прогревали, использовали seed=1234 и num-prompts=32; ошибки исключали из медиан производительности, но учитывали отдельно.

Дополнительно сравнили mooncake и nixl на InfiniBand, провели настройку параметров sglang и mooncake, а также отдельный тест attention backend triton против fa4. Для последних проверок выборки были небольшими — обычно 2–3 тёплых повтора.

## Результаты
В основной матрице при конкурентности 8 RDMA снизил медианный TTFT в 5,4–11,5 раза на трёх профилях с опубликованными валидными сравнениями и повысил output throughput в 2,8–3,8 раза. TPOT оставался близким: 10,8–11,7 мс для IB и 10,0–10,5 мс для TCP, что согласуется с влиянием переноса KV преимущественно на время до первого токена. Все 75 прогонов IB были валидны; у TCP успешны 44 из 75, а 31 завершился отказом. Особенно тяжёлые профили 2048/2048 и 32768/256 провалились во всех повторах при всех проверенных уровнях конкурентности; 8192/256 выдержал конкурентность 8, но при 32 имел один отказ из пяти.

Логи TCP-отказов начинались с ошибки копирования из CUDA memory с out of memory, затем возникал таймаут KV-transfer через 300 секунд, завершался prefill, а router возвращал HTTP 503. Изолированный тест transfer_engine_bench воспроизвёл отказ TCP с VRAM-буфером. По счётчикам TCP шёл через bond0, а IB — через InfiniBand. TCP достигал максимум 8,7 Гбит/с из 200 Гбит/с Ethernet; IB — 61,7 Гбит/с против примерно 2933 Гбит/с суммарного измеренного потолка восьми NDR-портов. Насыщение фабрики не подтверждено. В L0b GPUDirect превзошёл host staging на 6,29% для записи и 6,50% для чтения; TCP write из VRAM завершился ошибкой.

nixl работал по сопоставимому IB-маршруту: различие объёма передачи по счётчикам не превышало примерно 1%. В отдельной проверке triton дал TTFT на 33,5–44,4% ниже fa4 и throughput на 17,7–19,9% выше, но использовал другой KV layout. Большинство проверенных настроек sglang и mooncake не улучшили базовый результат; MC_NUM_QP_PER_EP=4 приводил к зависанию decode.

## Ограничения
Выводы относятся к одной конфигурации: MiniMax-M3 MXFP8, конкретной сборке sglang/mooncake и двум узлам с B200. Другие модели, точности, KV-layout и транспортные варианты не проверялись; использовался только один decode-узел. 31 неудачный TCP-прогон исключён из медиан производительности, поэтому успешные TCP-результаты подвержены смещению выборки, хотя частота отказов показана отдельно. M2 проводился на холодном стеке и его абсолютные TTFT нельзя напрямую сопоставлять с прогретой M1. Тесты настройки и сравнение attention backend имели малые выборки. fa4 и triton работали с разными KV-layout (page_size=128 против page_size=None), поэтому выигрыш triton не доказывает эквивалентность качества и производительности на длинных контекстах или при speculative decoding. Production-нагрузки, p99, память и масштабирование авторы не проверяли.

## Что взять себе
- Для PD-инференса оценивайте TTFT, TPOT и долю отказов вместе: хорошая скорость на успешных TCP-запросах не раскрывает проблемы надёжности тяжёлых KV-профилей.
- Проверяйте фактический маршрут KV по приращениям счётчиков сетевых интерфейсов и отдельно измеряйте программный путь переноса; номинальная полоса сама по себе не объясняет стоимость host staging.
- В тестовую матрицу включайте длинные входы, длинные выходы и их сочетания: объём KV на запрос может быть важнее одной лишь конкурентности.
- Не переносите преимущество triton на production без проверки KV-layout, длинных контекстов, качества ответов и потребления памяти.
- Прогревайте стек и ставьте health-gate после прогонов, чтобы не смешивать холодный старт и измерение живого prefill-сервиса.
